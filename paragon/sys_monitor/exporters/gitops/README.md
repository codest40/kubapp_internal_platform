# GitOps Exporter

The `gitops` exporter provides **GitOps and ArgoCD visibility** for `sys_monitor`.

While the GitHub exporter observes activity coming from GitHub, this exporter looks at the **actual state of applications running in the Kubernetes cluster**.

Its primary purpose is to expose GitOps state as Prometheus metrics so that the monitoring stack can determine whether applications are healthy, synchronized, degraded, or drifting from their desired state.

## What It Does

The exporter periodically connects to the target Kubernetes cluster and queries ArgoCD `Application` resources.

It calculates metrics such as:

* Total GitOps applications.
* Healthy applications.
* Out-of-sync applications.
* Degraded or missing applications.
* GitOps drift ratio.
* GitOps convergence score.

The metrics are exposed through a Flask HTTP service on port `9105`.

The basic flow is:

```
Kubernetes / EKS
      │
      │
      ▼
ArgoCD Applications
      │
      ▼
GitOps Collector
      │
      ▼
Prometheus Metrics
      │
      ▼
/metrics :9105
```

## What Must Already Exist

The exporter expects the following infrastructure and services to already exist.

### Kubernetes / EKS

A reachable Kubernetes cluster must exist.

The exporter currently expects an **Amazon EKS** cluster because it uses AWS APIs and the AWS CLI to obtain cluster information and authentication tokens.

The target cluster is identified through:

```
TARGET_CLUSTER_NAME
TARGET_REGION
```

### AWS Credentials / IAM

The runtime environment must have AWS credentials capable of:

* identifying the current AWS account,
* calling EKS `DescribeCluster`,
* obtaining an EKS authentication token,
* and, when using cross-account mode, assuming the configured target IAM role.

In local mode, the exporter uses the current AWS identity.

In cross-account mode, it assumes:

```
TARGET_ROLE_ARN
```

### ArgoCD

ArgoCD must already be installed in the target Kubernetes cluster.

The exporter reads ArgoCD `Application` custom resources using:

```
argoproj.io/v1alpha1
applications
```

The exporter does not create or manage ArgoCD applications. It only observes their current state.

### Kubernetes RBAC

The AWS/IAM identity used by the exporter must ultimately have sufficient Kubernetes permissions to read the required resources.

The client performs a node-access check during initialization as an additional RBAC diagnostic.

### Prometheus

Prometheus should already exist to scrape the exporter.

The exporter exposes:

```
http://<host>:9105/metrics
```

Prometheus can then collect the GitOps metrics.

## Directory Structure

```
gitops/
├── README.md
├── requirements.txt
└── src/
    ├── app.py
    ├── collector.py
    ├── k8s_client.py
    └── metrics.py
```

### `app.py`

Runs the HTTP service.

It provides:

```
/
/metrics
```

The `/metrics` endpoint exposes the metrics generated by the exporter.

A background worker also runs the collector every 30 seconds.

### `collector.py`

Contains the GitOps collection logic.

It:

1. Creates or obtains the Kubernetes clients.
2. Queries ArgoCD `Application` resources.
3. Examines application health and synchronization status.
4. Calculates GitOps metrics.
5. Updates the Prometheus gauges.

The collector is therefore the component that translates **ArgoCD state into monitoring signals**.

### `k8s_client.py`

Provides the Kubernetes client used by the exporter.

It handles:

* AWS session creation.
* Local AWS authentication.
* Cross-account role assumption.
* EKS cluster discovery.
* EKS authentication token generation.
* Token caching.
* Kubernetes API client creation.
* RBAC diagnostics.
* Failure backoff and circuit-breaker behavior.

This separates AWS/EKS authentication and Kubernetes connection management from the actual GitOps collection logic.

### `metrics.py`

Defines the Prometheus metrics exposed by the exporter.

The main signals are:

| Metric                         | Meaning                                         |
| ------------------------------ | ----------------------------------------------- |
| `gitops_app_total`             | Total number of ArgoCD applications             |
| `gitops_app_healthy_total`     | Number of healthy applications                  |
| `gitops_app_out_of_sync_total` | Number of applications not synchronized         |
| `gitops_app_degraded_total`    | Number of degraded or missing applications      |
| `gitops_drift_ratio`           | Proportion of applications that are out of sync |
| `gitops_convergence_score`     | Proportion of applications that are healthy     |

## Authentication Modes

The exporter supports two operating modes.

### Local

In local mode, the exporter uses the AWS identity already available to the runtime environment.

```
CLUSTER_MODE=local
```

This is intended for situations where the exporter and target EKS cluster are accessible using the same AWS account/identity.

### Cross-Account

In cross-account mode, the exporter assumes an IAM role in the target AWS account.

```
CLUSTER_MODE=cross
TARGET_ROLE_ARN=<target-role>
```

This allows the monitoring system to observe an EKS cluster located in another AWS account without requiring long-lived credentials for that account.

## Runtime Configuration

The exporter reads its configuration from environment variables.

| Variable              | Purpose                                        |
| --------------------- | ---------------------------------------------- |
| `CLUSTER_MODE`        | Selects local or cross-account operation       |
| `TARGET_CLUSTER_NAME` | EKS cluster to observe                         |
| `TARGET_REGION`       | AWS region containing the cluster              |
| `TARGET_ROLE_ARN`     | IAM role used in cross-account mode            |
| `ENABLE_NODE_DEBUG`   | Enables additional Kubernetes node diagnostics |

Defaults are provided for some values, but production deployments should explicitly provide the intended target configuration.

## Metrics Collection

The collector runs continuously.

The current collection interval is:

```
30 seconds
```

Each collection reads the current ArgoCD application state and updates the Prometheus gauges.

For example, if there are 10 ArgoCD applications and 8 are healthy:

```
gitops_app_total = 10
gitops_app_healthy_total = 8
gitops_convergence_score = 0.8
```

If 2 applications are out of sync:

```
gitops_app_out_of_sync_total = 2
gitops_drift_ratio = 0.2
```

These values allow Prometheus and Grafana to represent the current GitOps state of the platform.

## Relationship With SysMonitor

The GitOps exporter represents the **Kubernetes/GitOps side** of `sys_monitor`.

The broader monitoring system can therefore observe multiple layers:

```
GitHub
   │
   ▼
GitHub Exporter
   │
   ▼
GitOps / ArgoCD
   │
   ▼
GitOps Exporter
   │
   ▼
Kubernetes
   │
   ▼
SysMonitor
```

This allows `sys_monitor` to correlate external development activity with the state of the deployed platform.

## Important Boundary

The GitOps exporter is **observational**.

It does not:

* deploy applications,
* synchronize ArgoCD applications,
* modify Kubernetes resources,
* modify AWS infrastructure,
* create IAM roles,
* create EKS clusters,
* or manage Terraform state.

Its responsibility is to **observe GitOps state and expose that state as monitoring data**.
